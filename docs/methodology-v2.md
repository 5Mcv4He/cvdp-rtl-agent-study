# Methodology V2：从 RTL 调试行为到强化学习任务候选

版本：V2 方法审查与设计，2026-11-22。审计基线：`35fdf72979480824133ef6140f58f4f08beba9d2`。

**项目目标是发现专业工程任务中的模型能力问题，验证其成因，并把有训练价值的问题转化为可执行的任务、环境和可靠反馈。** ACE-RTL 与 DeepSeek Harness（DSH）提供观察模型行为的实验系统。通过率是诊断入口；项目的主要交付是行为数据、能力缺陷证据、RL 任务候选和奖励质量审查。

本轮完成代码与实际本地记录审计、八类案例审查和下一阶段设计。没有调用付费模型，没有重跑历史评分，没有安装系统软件，没有实现下文规划的功能。V1 的实验、原始记录和分数保持不变。本文是后续方法的入口；[旧协议](protocol.md)中的拟定条件不能视为 V1 全部已经实现。

## 1. 当前能得出的判断

1. **已有数据足以启动案例级诊断。** 已定位八组对照全部 192 个试次的本地记录，并核对额外 48 个工具开关试次。可以查看外显请求或会话事件、候选、判分和部分系统决策，提出具体而可检验的假设。
2. **还不足以建立统一的、逐动作可重放的行为数据集。** 早期 DSH 没有独立的 API 请求体记录；工具运行只在每轮末保存目标文件，缺少每次工具执行后的文件状态；异常和恢复记录还没有统一关联 ID。
3. **系统差异已经影响“能力”的解释。** ACE 的 126 份候选中，67 份有后处理操作，其中 39 份包含 `always_comb` 到 `always @*` 的转换。DSH 没有同样的转换。工具开关还同时改变了交付方式、可见证据和请求消耗结构。
4. **现有通过表示通过原 CVDP 测试。** 它不证明实现满足全部专业规格。加法器检查器存在随机输入未断言的问题；等差数列题需要审查公开规格、接口宽度和检查器约定是否充分对齐。
5. **目前没有已证明有效的 RL 训练数据。** 可以提出两项优先任务候选和一项待澄清候选；仍需诊断、独立验证、许可及数据隔离审查。没有训练与独立评测证据，不能宣称提升了基础模型能力。

推荐最近一步：先把本文八类案例的证据链结构化，并离线检查后处理、规格和评分器。达到记录与验证门槛后，再申请一项固定 DeepSeek Flash 的小规模诊断实验。

## 2. 两个实验的科学问题

### 实验一：在固定 ACE 系统中观察不同模型

问题是：同样的任务输入和工程流程下，不同模型会产生哪些可重复观察的错误？这些错误在反馈后如何变化？哪些解释具有训练任务价值？

分析单位分为任务、试次、实际模型调用、候选版本和验证事件。角色名称不能替代实际调用计数。首次候选必须同时保留原始输出、提取结果及后处理后受测版本。

预期产出是带证据的能力假设，例如“在明确的复位规格下，某配置反复生成错误极性的实现”。要进一步归因为规格提取、语言表达或时序理解，需要在固定错误候选上做诊断。单次修复成功仅证明这次候选发生了有效改变。

V1 四模型 ACE 比较保持为**系统条件下的表现观察**。DeepSeek 关闭思考，Claude/GPT 使用 `low` 推理；API 协议、供应方和实际计算量不同。可以比较这些配置的输出，不能称为等推理预算下的模型能力排序。

### 实验二：固定模型，研究 Harness 改变了哪些可观察行为

分成两类，分别登记、分别报告。

| 类别 | 设计 | 能回答的问题 | 不能据此推断 |
|---|---|---|---|
| 自然系统对照 | 保留 ACE 角色与编排；DSH 开启原生文件与命令交互；固定题目、模型、外部评分与资源边界，公开各自机制 | 哪些信息被提供、哪些动作发生、在哪一步出现结果分歧 | 单一组件的因果贡献 |
| 机制诊断 | 固定同一份候选、模型和预算，单独改变一种证据、处理步骤或执行条件 | 被干预因素是否改变了指定行为或失败现象 | 完整 Agent 的总体排名或跨任务稳定能力 |

自然系统也需要研究用的安全边界：保持角色编排不意味着让求解器读取隐藏验收源码。应显式规定 ACE 可访问的公开材料、DSH 可执行的工具，以及反馈服务提供的信息。与上游默认行为不同的地方都进入 manifest。

V1 的 192 次矩阵是 ACE 精简反馈配置与**关闭工具的 DSH 辅助条件**的比较。48 次工具开关实验是 DSH 内部的配置对照。两者都不能改名为已经完成的 ACE 与完整 DSH 自然系统对照。工具组使用普通子进程 bash 替代 PTY shell，也是需要保留的实际配置差异。

每次 Harness 修改都要对应一个测量缺口或诊断假设。仅能提高当前测试通过数、不能增加能力或任务质量认知的修改，暂不列为主要研究工作。

| 批次 | 本轮核对的实际文件 | 记录完整性的结论 |
|---|---|---|

192 次矩阵中，183 次可由私有批次索引直接连接；其余 9 次由首候选哈希唯一定位，再从原第二轮响应提取代码，**9/9 与公开第二候选哈希一致**。这 9 次没有正常结束的原始 `result.json`，公开报告已记 `offline_replay` 且耗时为 null。可恢复代码与结果关联，不能恢复当时正常结束所需时间。

DSH 矩阵中的 130 份评分候选包含这 9 份离线提取候选；两次 Claude 咖啡机截断没有可评分候选。192 是逻辑试次总数，包含此前请求前修复后的补采以及离线恢复，不能当成 192 个未经任何中断的进程。此前 4 个请求前输入限制恢复由 `apply_recovery` 单列；另有 8 次长输入补充请求在 [补充诊断](../experiments/suite/context-limit-results.json) 中，不并入 192 或 48 的主结果。

工具开关的 15 次预算耗尽中，14 次有中转拒绝记录；另一次由运行器在首轮后发现额度已满、未继续第二轮而结束。因此拒绝次数和预算耗尽试次数不同。

### 3.3 八项审计问题的逐项结论

| 问题 | 证据与当前判断 | 限制 / 是否重新采集 |
|---|---|---|
| 1. 每次调用及实际可见上下文可否重建？ | ACE 的 E4/E9 保存已序列化请求体；工具 DSH 的 E6/E11 保存每次 body。早期 DSH 的 E5/E10 有系统、用户、响应和 inbox 事件，后续轮次依赖已有会话状态 | 早期 DSH 只能称 SDK 层重建，不能冒充线上的完整请求。新诊断需捕获最终请求体；旧批次无需整体重跑。供应方内部附加内容、默认采样及实际内部思考均不可观测 |
| 2. 响应、工具、代码、反馈和决策是否可关联？ | ACE 有按请求序号及迭代目录组织的链；DSH 有 session、seq、turn、step；工具 174/174 结果有对应 call ID | 缺跨系统统一 ID，ACE 角色与 HTTP 调用需对照内容；工具每轮末才保存文件，bash 写文件的中间状态无法保证恢复。旧数据离线索引，新采集增加逐动作状态 |
| 3. 原始输出与后处理是否分开？ | ACE 有 provider response、`generator.response.json`、提取产物、`.sv.raw`、后处理记录及受测候选；DSH 有 `final_response` 和解析后 RTL | ACE 126 份候选中 67 份发生变化：39 份清除模块外说明、39 份降低 `always_comb`，交集 11。这个操作记录中的 “reasoning” 只是上游字段名，不能认定为内部思考。V2 必须显式分层；旧材料可离线核对 |
| 4. 失败在哪一步？ | E7 提供 compile/functional/timeout/infra；E6 区分 finish、快照、已完成候选、拒绝原因；详细日志能补充首个错误 | 批跑异常经常压成 `runner_error + exception type`，预算前拒绝不一定有 API 记录。不能仅用最终 outcome 定位全链。新采集要保证异常 finally 落盘，并记录首阻断点与最终终止原因 |
| 5. 什么没有被捕获？ | 已检查实际文件和 E4–E11 写入点 | 缺统一动作前后文件哈希、完整进程退出/超时结构、逐请求剩余额度、统一 Harness 决策事件、实际安装产物与本地补丁的逐运行指纹；工具返回文本不等于完整 stdout/stderr。历史缺失记 unknown；新采集补齐 |
| 6. 预算、采样和权限一致吗？ | 见第 4 节，已核对请求体/SDK 头与设计 | 轮数、请求上限、可用额度、总 token 和计算量不同。不能用“同两轮”或“同八请求上限”称等预算能力比较 |
| 7. 评分支持什么能力结论？ | E7 检查实际受测字节、非空测试计数与原测试结果；E12 提供局部独立证据 | 编译是工具链下的表现；functional 不是能力标签；原测试重放不是未见测试。需要规格—检查项映射、正反对照和独立测试后才能升级结论 |
| 8. 能设计训练任务吗？ | 已有可定位的复位错误、进位错误、重复代码、截断和交付案例 | 足以形成任务需求及诊断假设，不能直接导出可信 RL 样本。仍缺独立 Reward、环境契约、许可清单、训练/评测隔离及稳定性验证；无需为这些缺口重跑全部模型 |

## 4. 实验条件与必须降低强度的表述

### 4.1 设计与实测条件

| 条件 | ACE 矩阵 | DSH 无工具矩阵 | DSH 工具开关 48 次 |
|---|---|---|---|
| 每题重复 / 候选轮次 | 2 / 最多 2 | 2 / 最多 2 | 2 / 最多 2 |
| 模型请求上限 | 4，含角色调用与重试 | 轮次约束通常最多 2，禁用自动重试 | 两侧中转硬上限 8；无工具流程通常只能用 2 |
| 输出上限 | 每请求 4096 token | 每请求 4096 token | 每请求 4096 token |
| 输入限制 | 实际请求体 48,000 字节 | 当前公开初始 prompt 24,000 字节、上轮回复 16,000 字节门槛；历史请求前恢复另记 | 初始 prompt 24,000 字节，所有请求体 48,000 字节 |
| DeepSeek 采样 | 实际 body 为 temperature 0.2、top_p 0.95、thinking disabled | SDK 记录 reasoning off；没有独立 wire body，不断言供应方默认采样值 | 224 个 body 均未传 temperature/top_p，thinking disabled |
| Claude/GPT | MiCu 原生协议，推理 low；与 DeepSeek 的参数不同 | 同一对应服务分组，SDK 原生供应方插件、推理 low | 未涉及 |
| 求解证据 | 精简外部评分类别、角色历史与建议；隐藏 harness 上下文被关闭 | 同类别反馈与 SDK 会话 | 类别反馈；工具组另可读写文件、自建测试、编译仿真 |
| 交付与处理 | 提取、原生兼容性后处理，再评分 | 文本提取，没有 ACE 对应兼容性处理 | 关组提取完整文本；开组读取工作区目标文件，并区分完成提交与截停快照 |
| 时间 / 并发 | 模型与评测各有超时，可按批次 workers 并发 | SDK 请求超时 95 秒 | SDK 95 秒，bash 工具配置 300 秒；实际批跑使用四 worker |
| 随机性 | 仿真 seed 20261122；没有固定模型 seed | 同左 | 同左 |

没有统一总 token 或端到端墙钟硬预算；相同输出 token 限额也不保证相同可见代码长度或推理计算量。模型名称和服务返回名不能证明后端权重在所有批次间不变。矩阵的补齐批次先后进行，任务轮换也不等于完整随机、同时交错的试验。

`docs/protocol.md` 写过串行、相同预算及应保留完整请求等目标；实际批跑支持并发，日志覆盖有上述差别。V2 用实际配置和证据填写 manifest，禁止将草案直接复制成“已控制变量”。

V1 数字冻结；V2 的派生标签、离线诊断和独立分数另存，带原始记录引用及方法版本。

## 5. 关键方法缺口及修复顺序

**P0：会导致错误归因或错误奖励的缺口。** 原始输出与后处理效果未进入分析；每次实际模型输入覆盖不一致；失败类别混入系统终止；规格/Verifier 尚未逐题对齐；训练与评测用途未登记。先解决这些问题，再谈更多模型、题目或调用。

**P1：会妨碍定位机制的缺口。** 缺少统一事件因果链、逐动作候选快照、完整反馈可见性和预算状态。纯粹增加最终通过率样本不会补上这些信息。

**P2：扩展能力。** 多题打包、多模型路由、复杂过程奖励、训练框架均后置。此阶段不构建通用 RL 平台。

还存在两个具体工程风险，属于下一阶段验证范围：

- `run_dsh_tools_study.py` 顶部说明仍提到内层 sandbox-policy / persistent shell，实际执行是外层约束加普通 bash。`fingerprint()` 当前覆盖脚本、配置文本和运行时路径，未对运行时二进制及所有间接依赖取内容哈希。不能把旧验收指纹解释为整个环境已完全固定。
- 现有文件约束禁止读取工作区树与用户主目录中的保护内容，但以 `allow default` 为起点，系统临时区仍有权限；这不等于“只可读 solve”。评分器的清洁环境及若干 RTL 字符串拦截也不等于独立 OS 权限边界。训练候选门槛需要同时覆盖求解侧、共享临时区、评分侧和任务间隔离。本轮没有新增任何绕过或攻击测试。

## 6. 八类代表性案例审查

这些案例按现象选取，用于诊断，**不用于估计总体失败类别占比**。每项由 task、condition、repetition 和哈希前缀定位；完整哈希在公开结果或 P2 记录。字段解释：O 为直接观察；H 为机制假设；I 为干预支持。源码分析与历史人工修正也只能支持其实际验证范围。

### C1 · 首次成功：64b/66b，ACE＋Claude，重复 1

- **O**：一次 Generator 请求，首候选 `5558fee567cf…` 通过 10 个原测试；响应、提取后文件、评分哈希可关联。重复 2 也得到相同候选哈希。
- 支持“该配置在这两次求解中完成原测试要求”；不能证明整个编码协议、所有复位时刻及未测控制组合正确。
- 无需新模型请求。下一步用规格驱动的独立复位/控制覆盖复核，作为修复任务的正对照候选，状态为 `needs_reward_review`。

### C2 · 失败后修复：64b/66b，ACE＋Flash，重复 1

- **O**：候选 `4405da850a17…` 在复位检查失败；第二候选 `5558fee567cf…` 通过。diff 显示两个时序块的低有效复位改为高有效。API 链为 Generator → 两次 Reflector → Generator。
- 第二轮能看到精简类别和角色生成的建议；不能把详细复位断言自动视为模型已经看到。重复 2 同样首败后过，可作为补充证据。
- **H**：初始规格对齐错误；角色提示重新强调复位；或再次生成自然修复，均可能。
- **待验证**：固定首候选，对照无新增证据、类别反馈及独立复位反例。指标是复位约束是否纠正、是否引入时序回归，不仅看总 pass。

### C3 · 重复提交及测试覆盖：Brent–Kung，P2 ACE＋Flash

- **O**：四次请求、两次候选均为 `f7de4b799a28…`，原测试同一进位检查失败。已有独立算术记录为 4,075/4,128 输入失配。原请求与两次评分在本地仍存在。
- **O**：本轮重新运行只读静态审计，确认题面与检查器的 12 个固定向量相同；10 个随机向量的循环没有 assert。这里确认的是覆盖缺口，尚未构造“只记固定答案”的实现去证明假阳性。
- **H**：反思建议缺少正确根因、建议未进入最终请求、建议进入但未落实，须分别检查。相同受测字节本身无法区分这些解释，也不代表内部没有发生推理。
- 下一步先对齐两份原始输出、角色建议和第二次 Generator 实际输入，再考虑固定失败候选的证据对照。开发题不再作为独立评测集。

### C4 · 持续失败与规格疑点：等差数列，ACE＋GPT

- **O**：重复 1 的 `52f71315f4d8…`、`d19537f3f4e3…` 都在输出宽度检查失败；diff 只见条件表达顺序调整。重复 2 两份候选哈希相同，也失败。
- **I（已有人工代码干预）**：本地诊断把第二份候选的最小宽度增量改为至少 1，得到 `9395f8ad6b13…`，已有重放记录通过。只支持该宽度改动解释这次评分变化，未证明其完整规格正确，也未验证模型怎样利用反馈。
- **疑点**：公开题面重点是长度 0 时稳定输出；检查器还约束内部/输出宽度。必须联合原始 RTL 接口、允许修改范围及参数域判断该约束是否充分公开。当前不能直接断言 Verifier 错误，也不能归为模型不懂数学。
- 此任务暂列 `quarantined_spec_review`。先完成规格裁决；未解决前不导出 RL 正负标签。

### C5 · Harness 结果不同：状态机，GPT，重复 1

- **O**：ACE 首候选通过，记录了 `always_comb` 兼容性转换。DSH 首候选 `8816880410c1…` 编译失败，原仿真日志明确有 8 个“需要显式 cast”的赋值错误；第二响应提取哈希 `61592bf0485a…` 与已发表通过候选一致。
- **限制**：两套模型输出不同。ACE 有转换与 DSH 有编译错误同时发生，不足以证明前者导致结果差异；尤其不能把 cast 错误直接解释为 `always_comb` 问题。
- 下一步固定同一份原始代码，分别只提取、应用单项兼容性处理，离线编译/评分。先测后处理的实际影响，再决定是否需要模型诊断。

### C6 · RTL 已过但未交付：通用计数器，工具开组，重复 1

- **O**：8 次模型请求、8 个工具调用，首轮以预算耗尽终止，无 completed submission；工作区快照通过原测试。工具事件可通过 call ID 对齐。
- 直接支持“结束流程与工作区正确性应分开记录”。不能据此认为模型不会实现计数器；也不能认定快照在第 7 次请求时就已正确。
- 下一步检查逐动作可恢复性，设计终止规则诊断。新运行捕获每步状态，才可确定首次形成通过候选的时刻。

### C7 · 自建验证与最终终止不同：RGB→YCbCr，工具开组，重复 2

- **O**：工具返回中记录自建仿真超时，此后继续有模型请求；最终按八次请求预算结束，工作区快照通过原测试。
- 不能把最终 `budget_exhausted` 覆盖掉更早的工具阻断，也不能把 `tool/result.isError` 单独当作退出码。此类事件需保留返回内容、超时事实和最终终止的多级分类。
- **H**：测试台终止条件、握手安排、候选行为或工具超时策略均可能影响。下一步首先离线审查自建测试台及日志。原工具返回还显示后续命令调用了本环境不存在的 `timeout` 程序（exit 127），应单列工具兼容性事件；未查明前不贴“不会验证”的标签。

### C8 · 长任务的不同失败环节：咖啡机

- **O**：DSH＋Claude 的两次矩阵记录均 `max-tokens`，最终文本都没有 `endmodule`，没有完整可评分候选。工具开组同题两次则触发请求体积限制；这与输出截断是两种不同限制。
- 支持输出/上下文预算诊断。现有记录不能比较“文本重写”和“文件编辑”谁具有更强工程能力，因为模型和批次也不同。
- 先离线统计输入组成、截断位置和交付契约；如需付费诊断，固定一个模型、候选和预算，只改变表达或反馈条件。禁止把这两种失败直接用作 RTL 功能负样本。

## 7. V2 三层数据结构

复用现有 JSON/JSONL 和目录，不引入数据库或大型训练框架。默认原始层私有；公开只导出白名单字段、经过审查的案例说明和代码。所有派生字段记录来源，缺失用 null 加原因。

### Layer A · Behavior Trace

建议三个文件：`manifest.json`、追加式 `events.jsonl`、内容寻址的私有 `artifacts/`。历史转换产物存 V2 独立目录并引用 V1，不能覆盖旧文件。

| 对象 | 最小字段 |
|---|---|
| Run manifest | schema_version、run_id、V1 来源、task_id、task_family、dataset/row hash、split/purpose、model requested/reported、provider/protocol、Harness 与补丁/runtime/scorer 指纹、工具权限、初始文件清单、预算与 seed、并发及时间 |
| 事件公共字段 | event_id、run_id、seq、wall_time、monotonic_time（不可恢复则 null）、type、actor、parent_event_ids、artifact_refs、evidence_level、missing_reason |
| Model request | call_id、角色/用途、实际最终 body 的私有引用与 hash、可见消息/工具/反馈引用、采样参数（区分 omitted 与明确值）、剩余额度、发送/拒绝状态 |
| Model response | call_id、provider ID、外显内容引用、usage、finish_reason、传输错误；不可获取部分记 unknown |
| Tool action / result | call_id、动作与参数引用、执行工具/version、工具结果、stdout/stderr 引用及截断标记、exit code/timeout、耗时、动作前后目标及工作区清单哈希 |
| Candidate | candidate_id、parent_candidate_id、来源（raw/extracted/transformed/workspace/submitted）、原始响应引用、变换名称与版本、文件字节哈希及 diff、交付状态 |
| Feedback / verifier | feedback_id、对应 candidate/verifier、实际交给谁及哪次请求、内容引用；verifier_id、版本/测试 hash、seed、运行环境、检查项数、verdict、反例引用、是否模型可见 |
| Harness decision / resources | 输入事件引用、规则版本、继续/重试/重置/截停/接受、明确原因、额度前后变化、请求/工具/评分消耗 |

证据等级：`captured_wire`、`captured_sdk`、`captured_file`、`derived`、`inferred`、`missing`。完整上下文指受信发送端实际提交的输入；不能延伸成供应方内部输入或思维过程。

顺序以进程内 seq 为准，时间戳辅助。父事件表示有证据的依赖关系，不能仅凭相邻时间推定因果。分开记录“反馈已生成”“已加入待发输入”“实际请求携带”；没有最终请求记录时不声明最后一种。

工具调用成功只说明执行完成；必须用文件哈希和评分确认候选变化。工具返回文本、自建测试结论和受信 Verifier 结果使用不同事件类型。

### Layer B · Capability Diagnosis

每个案例一份诊断卡，至少包括：

- case_id、关联事件/候选/试次、选择理由及范围。
- observed_failure、first_blocking_step、terminal_outcome。
- 模型能力候选标签、Harness/工具/Verifier 等替代解释。
- 支持证据、反驳证据、缺失证据；观察与假设分栏。
- 置信状态：`unresolved`、`plausible`、`intervention_supported`、`replicated_in_scope`。附范围与理由，不伪造数值概率。
- 预注册干预、控制变量、预期可区分的结果、实际结果和假设修订历史。
- 是否可进入训练任务设计，未通过的门槛及负责人审查记录。

分类使用两个独立轴：

| 轴 | 标签示例 | 使用要求 |
|---|---|---|
| 执行结果 | compile、functional、sim_timeout、tool_timeout、no_submission、output_truncated、request_budget、input_limit、transport_error、infra、pass | 根据记录定位；可同时标注首阻断与最终终止 |
| 原因假设 | specification_alignment、arithmetic_width、temporal_protocol、HDL_semantics、evidence_acquisition、feedback_application、delivery_control；以及 extraction、postprocess、context_loss、tool_compatibility、verifier_gap、spec_ambiguity、resource_limit | 前一列不自动映射本列；多假设并存，并允许 unknown |

标注先做 8 案例，按同一规则复核。不同审查者或两轮复核不一致时保留分歧，不用多数票掩盖规格冲突。哈希相同只标“字节相同”；只有经过语义分析，才标“相同语义错误”。

### Layer C · Training Task Candidate

一个候选包的最小结构：`task.json`、公开输入与初始工程、环境契约、受信 verifier manifest、正反对照清单、quality report、license/provenance、split registry。验收源码、答案及原始轨迹不放进求解侧，也不随公开导出默认发布。

`task.json` 包含 target_capability、diagnosis_refs、公开规格与歧义裁决、输入/初始状态、允许动作、交付契约、终止政策、资源边界、Verifier/Reward 版本、已知正确/错误对照、难度依据、来源与许可、训练/评测用途、局限。

生命周期：`proposed → diagnosed → environment_validated → reward_reviewed → eligible_for_training_study`。许可证、规格或隔离未过可进入 `quarantined`。达到最后状态仍仅表示可用于训练研究，不代表已训练有效。

## 8. 最小诊断实验设计

下列均为**计划**。本轮未执行新的模型实验，也未执行下表新的仿真干预。先批准并完成离线阶段，再确认具体付费设计；不一次性跑完所有选项。

| 编号 | 固定项与干预 | 最小规模 / 预算上界 | 主要可检验结论与反证 |
|---|---|---|---|
| D0 · 证据链验收 | 原始文件不变；解析八类案例，验证请求→响应→提取→受测字节→反馈引用；重建未知项清单 | 离线，0 模型请求 | 能恢复哪些链。无法恢复的步骤明记 missing，不通过合成日志补齐 |
| D1 · 后处理影响 | 固定 C5 的原候选、Icarus、scorer；比较仅提取与单项兼容性处理。每个因素独立切换 | 先 2 份候选 × 2 条处理路径，4 次离线评分；有必要才扩展单项处理 | 原代码/处理后有结果变化才支持该处理的作用。两边同失败则反驳其足以解释差异。不能用两个 Harness 各自输出代替同一输入 |
| D2 · 规格与 Reward 审查 | C3 公开算术规格、C4 完整接口契约；原测试保持不变，另写独立检查与正反对照 | 每任务先 1 正、1 原错、3 种定向错误实现；每版同种子重放 3 次；0 模型请求 | 检查器是否漏检/错拒。C4 规格无法裁决则停在隔离区，不强行赋错对标签 |
| D3 · 反馈利用诊断（首选付费项） | 固定 Flash/off、同一个失败候选、同一求解提示与无工具环境；A 仅重复修复请求，B 加类别反馈，C 加独立规格反例；每次新会话 | C2、C3 各 2 个重复 × 3 条件＝12 次求解；每次最多 1 模型请求、4096 输出、48,000 字节；无自动付费重试 | B 对 A 检验类别反馈的增量；C 对 B 检验证据具体性的增量。必须确认证据在最终请求中。若三组都修复，当前任务无区分度；若都失败，不能单凭此确认推理缺陷 |
| D4 · 自然系统小样本 | Flash/off；保留 ACE 角色编排与 DSH 文件/命令工具；外部评分类别、初始任务、评分和总请求边界统一 | 先 3 个已审案例 × 2 系统 × 2 重复＝12 次运行；每次最多 8 请求，上界 96 请求 | 找到具体信息/行动/交付差异，生成局部假设。相同上限不宣称相同实际推理量；分析以轨迹为主 |
| D5 · 交付机制诊断（备选） | C6 类型任务、Flash/off、同初始 RTL、同八请求限额；只改变第 8 次是否进入无工具的显式交付阶段 | 先 2 题 × 2 条件 × 2 重复＝8 次运行，最多 64 请求 | 同时记录第 7 次后的文件和最终文件。只有交付率改变而文件正确性未改善时，支持交付控制解释。代码或前序轨迹同时变化则限定结论；若可可靠恢复，优先从同一第七步状态分叉两种末步策略 |

D3 中反例来自独立公开规格检查器，不能把隐藏验收实现复制给模型。各条件保持同一非反馈文本和请求上限；反馈内容长度差作为处理的一部分单列，不能再声称严格等 token。题目/条件交错顺序在运行前登记，缓存与服务时间记录；两个重复只作可行性诊断，不能估计稳定能力分布。

如果 D3 的具体反例仍不能区分解释，可另申请“给出经过独立验证的故障根因”的一项后续条件。它用于检验实现已知修复的行为，不能混进未给根因的能力得分。

D4 必须解决 ACE 后处理记录和安全的反馈边界后再跑；D5 必须先获得逐动作文件快照。即使 API 费用可承担，也不自动扩大样本。每个实验输出一张“观察—假设—干预—结果—保留/否定解释—任务价值”卡；无法产生新信息就停。

## 9. 第一版 RL 任务候选规范

### 9.1 两项优先候选和一项暂缓候选

| 候选 | 目标、来源与输入 | Verifier / 正反对照 | 现阶段状态 |
|---|---|---|---|
| T1 进位归并修复 | C3 提供能力假设；以独立明确的 N 位无符号加法规格、初始错误归并网络和保留接口为输入，输出 sum 与 carry | 与独立 N+1 位行为模型比较；进位链、边界、固定与保留随机输入；正对照为规格实现；负对照包括原错、错误组索引、遗漏 carry、错误布尔运算 | proposed。已有开发题证据，尚未证明稳定模型缺陷；需许可审查与任务族隔离 |
| T2 复位与周期契约修复 | C2 提供假设；明确极性、同步/异步、复位中输出、解除后第一个有效周期以及数据/控制模式 | 独立逐周期 scoreboard；先写入非零状态再复位；正对照经过独立审查；负对照为极性错、复位漏清、一周期错位 | proposed。优先 D3，随后审查 Reward；不能把某次原测试通过候选直接当黄金答案 |
| T3 参数边界与宽度 | C4 的长度零/一、有限宽度行为；须先说明允许参数域、精确输出接口及溢出语义 | 规格明确后以边界与有限域穷举作对照；禁止仅模仿旧测试的内部变量约定 | quarantined_spec_review。未裁决前不做 RL 样本 |

先交付质量过关的 2 个包即可。不能为了凑 3 个，把存在规格争议的任务标成有效训练数据。实际训练用工程可独立编写，来源和衍生关系仍须如实记录；改名、改参数或换 seed 不会自动产生独立任务族。

### 9.2 环境契约

| 元素 | v0.1 约定与验收 |
|---|---|
| Reset | 从只读初始工程创建新工作目录，清除上次候选、测试产物和会话；初始文件哈希一致；运行同一 reset 两次得到相同观察 |
| Observation | 公开规格、允许编辑文件、工具说明、当前剩余预算与明确允许的反馈；禁止答案、隐藏测试、其他题材料、凭据 |
| Action | 先只支持 read/edit/write、受限 compile/run、submit；动作记录参数、结果和状态变化。文件路径与允许资源在 manifest 内固定 |
| Transition | 只修改本任务允许文件；每次动作保存可重建的差分或快照；工具失败也产生结构化事件；submit 冻结文件字节 |
| Reward | 受信外部 verifier 对冻结字节评分。采用终局二元正确性信号，另外记录交付、编译、检查覆盖及资源，不任意加权 |
| Termination | submit、动作/请求/时间耗尽、环境错误分别定义。预算耗尽后的快照正确性与完成提交分别记，不沿用含混的单一 final |
| Reproducibility | 记录 runtime、工具链、系统/镜像、verifier、题目和补丁指纹；固定候选可重复评分；行为日志重放不等于重新调用随机模型会得到相同输出 |
| Security | 求解进程与评分/答案/密钥分离；检查文件、链接、临时区、进程环境、网络和任务间可见性；评分侧也执行受限候选。验收失败即停止真实采集 |
| Data split | task family、来源、亲缘关系与历史暴露登记；训练、开发、最终评测及反馈专用测试分别分配；独立评测不得进入求解反馈 |

奖励建议明确区分 `correctness_reward` 与 `episode_status`：有效、已交付且满足规格时奖励 1；有明确反例、模型产生的编译失败或违反交付契约时为 0。Verifier/基础设施故障、规格未解决时 reward=null、样本无效，不能作为能力负例。超时必须先判明发生在工具、候选仿真还是环境，保留未知状态。

预算截停是否自动把目标文件算作终局交付，必须在新的任务契约预先选择。可以采用自动快照终评的环境以研究代码正确性，也可以要求显式 submit 研究交付；两者是不同任务定义。历史 V1 五个快照继续保留原分数。

过程指标先用于分析，例如是否获得有效反例、是否根据反例修改相关逻辑、是否产生新回归。没有验证这些指标与规格正确性的关系之前，不把“调用工具”“写测试”“文字解释较长”赋予额外奖励。

### 9.3 数据许可与评测隔离

代码仓库许可、数据集许可、单题上游来源以及模型服务对生成内容的使用条件分别核查，记录版本与来源。数据文件名中的 `no_commercial` 不能自动解释为数据训练许可。当前本地裸 JSONL 和锁文件不足以完成这项许可判断，候选包的许可状态保持待审。

现有 12 题和 Brent–Kung 已反复开发、分析，并在求解中收到同套测试反馈，登记为**暴露过的研究/开发材料**。其余 23 道 `cid016` 题也不能自动算独立测试：先检查使用历史、来源亲缘及公开预训练污染的不确定性，再做用途分配。更换 seed 只能隔离测试向量，不能代替任务级和任务族级隔离。

原始 CVDP 材料用于本研究诊断的依据，与未来训练授权分开管理。评测题上的修复样本不得加入训练后，又把该题成绩作为独立提升证据。

## 10. Reward Quality 检查规范

每包维护独立质量报告，逐项记录 pass/fail/not_tested、证据、Verifier 版本与局限。最低检查如下。

| 检查 | v0.1 必须提供的证据 / 失败处理 |
|---|---|
| 规格正确性 | 每个断言对应明确公开需求；接口、位宽、复位、延迟、溢出、参数域有定义；歧义未裁决则隔离 |
| 正对照 | 至少 1 个独立构造且经审查的正确实现通过；条件允许加入结构不同的第二实现。模型某次 pass 不等于黄金参考 |
| 负对照与变异 | 原始缺陷必须被检出；每个目标缺陷至少一个定向变异，首包至少 3 类实质不同错误；证明变异非等价，列出存活变异及原因。仅语法错被杀死不代表功能覆盖充分 |
| 漏检与错拒 | 错误实现通过、合规格实现失败分别调查；区分已知对照检出率和未知全部实现的真实性能，不能把变异分数称为真实假阳性率 |
| 覆盖与非空执行 | 测试数、实际检查计数、跳过/异常、仿真退出与目标文件 hash 可核对；随机输入须有 oracle 检查，`ALL PASS` 文本不作受信证明 |
| 稳定与重放 | 同一候选、环境、种子连续重放至少 3 次结果一致；另用预留输入检查覆盖。发现不稳定时排查调度/竞态，不能挑好的一次 |
| 反例有效性 | 保存规格需求、输入、期望/实际、必要时钟或状态引用；反例能在干净环境重现，反馈内容与独立终评内容分开 |
| 奖励投机 | 对只适配可见向量、常量输出、跳过行为、试图改验收等预设错误行为做受控拒绝/检出检查；测试及答案不可由求解者修改或读取 |
| 隔离与泄漏 | 重放现有金丝雀验收并扩充到任务间、临时目录与评分进程；记录各断言及实际边界，不仅写“scan clean” |
| 交付与预算 | 字节版本可追溯；工具结束、生成结束、提交接受和任务终止分开；超时/基础设施错误不会悄悄变成模型功能失败 |
| 许可与分割 | provenance、使用许可、暴露历史、任务族分组均通过审查，独立测试不会出现在请求或求解文件中 |

这些是首包工程准入标准，不是 Reward 绝对正确性的证明。质量报告必须列剩余未覆盖需求、不可判定情况和下一轮触发条件。对于异步跨时钟、真实物理时序等超出当前仿真模型的属性，要明确环境能力边界。

## 12. 扩展到 35、302 和完整 CVDP 的门槛

数据规模的定义先保持准确：当前锁文件中的 **35** 是指定 JSONL 内的 `cid016` 调试题数量；**302** 是该 `nonagentic_code_generation_no_commercial` 分区的总行数。302 不代表 CVDP 全部题目。当前 12 题经过可运行、原始 RTL 会失败等条件筛选，并含早先五题试跑，不能代表随机抽取的全部题目。

| 扩展阶段 | 必须先满足的门槛 |
|---|---|
| 继续八案例 / 首次 V2 诊断 | 八案例链条可核对；恢复与缺失显式标注；后处理影响可测；选择任务的规格明确；最终请求、资源与反馈可见性验收通过；付费设计获确认 |
| 扩至 35 道调试题 | T1/T2 至少两包通过质量审查；选定诊断能区分至少一个关键替代解释或明确证明原假设无支撑；新采集 100% 有稳定 ID、请求/工具/候选/评分关联，允许明确记录丢失但相应试次不得进入能力归因；逐题筛查规格、正反对照和可运行性；登记不可用题而不强行凑满；数据用途及调用计划获确认 |
| 扩至 302 行分区 | 按任务类别重做输入、动作、交付和评分适用性检查。现有 `task_row` 限制 `cid016` 且单目标，不能直接用当前 runner 全跑；各类别先小样本校准、独立质量审核、许可与任务族分割；证明新增任务提供新的能力信息 |
| 扩至完整 CVDP | 先列分区、任务类型、商业工具/许可、平台依赖、参考/验收可获得性与缺失处理；每种环境独立验收；有分层抽样、成本和数据治理计划。系统安装、实验条件改变及新增预算再次确认 |

如果增加样本只会产生更多 compile/functional 计数，却不能把错误定位到可检查的专业约束、机制或反馈问题，就暂不扩展。反之，一个得到反例支持、可以重置与可靠评分的任务候选，已经是本项目的数据策略成果；后续训练有效性需要另一个包含参数训练和独立评测的研究阶段。
