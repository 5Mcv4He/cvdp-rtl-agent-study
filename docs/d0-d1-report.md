# RTL 行为证据与后处理实测

本轮核验八类案例的 **12 次历史运行，共 244 个事件和缺失标记**，并固定四份历史模型回复，执行 **7 次离线评分**。使用已有本地数据，模型请求为 0。V1 正式成绩保持原样。 [方法定义](methodology-v2.md) · [D0 结构化结果](../experiments/v2/d0-results.json) · [D1 逐路径结果](../experiments/v2/d1-results.json)

## D0 从请求追到实际受测的代码

转换器为每个运行、事件和候选分配稳定 ID。私有证据引用包含文件路径、SHA-256 和 JSON 指针。事件按依赖排列，原始时间和 SDK 顺序从来源读取。候选 ID 独立于内容哈希，因此即使两轮字节完全相同，也能区分两次行为。

检查涵盖 42 份外显响应、24 对工具调用与返回、15 份候选及对应评分。ACE 用供应方响应的文本与结束状态核对被接受的 Generator 输出，重执行提取和后处理，再比对存档候选。工具运行用 SDK 步骤对齐中转账本，以工具调用 ID 核对响应、工具返回与后续请求。评分候选与实际受测文件及历史哈希必须一致。ACE 运行期间生成反馈所用的评估，与后来独立重放的评分分别引用。

| 案例 | 已核实的观察 | 仍待区分的解释与检查 |
|---|---|---|
| C1 64b/66b，ACE＋Claude | 首份候选通过 10 项原测试 | 独立时序与控制模式测试才能判断覆盖范围 |
| C2 64b/66b，ACE＋Flash | 精简失败反馈出现在后续请求，次份代码修正复位极性并通过 | 反馈、角色建议和再次生成都可能影响结果。需要固定首份候选，分别控制这些条件 |
| C3 Brent–Kung，ACE＋Flash | 四次请求产生两个字节相同的失败候选，精简反馈进入后续请求 | 仍需判别建议是否给出了根因，以及 Generator 是否把它落实到代码 |
| C4 等差数列，ACE＋GPT | 两次重复均连续失败。一次只重排条件，另一次两轮候选相同 | 仍需核对最小位宽在题面和接口中的定义 |
| C5 状态机，GPT | ACE 首轮通过。DSH 首轮有显式类型转换编译错误，次轮候选通过历史离线恢复评分 | D1 排除了所测转换足以解释差异。实际输入、候选写法和其他兼容性因素仍待区分 |
| C6 计数器，DSH 工具组 | 预算耗尽，无完成提交，工作区快照通过原测试 | 缺少逐动作版本，无法定位首次形成通过候选的时刻 |
| C7 RGB→YCbCr，DSH 工具组 | 自建仿真超时，后续命令遇到本机无 `timeout`，最终因请求预算停机，快照通过 | 自建测试台终止条件、握手和本地工具分别可能影响过程 |
| C8 咖啡机 | 无工具组两次输出截断并停在候选提取，所查工具组试次输入超限 | 逐请求分解上下文长度和输出截断位置，分别定位两个预算触点 |

六个 ACE 试次在检查范围内闭合。其余六个试次的已存环节通过核对，仍有 **11 项明确缺失**。无工具 DSH 有 SDK 会话事件，缺实际 HTTP 请求体。工具组有进入中转的请求，缺最终转发的串行化字节和逐动作快照。状态机的第二候选能与历史离线评分对齐，原进程没有保存外层终止记录。最后一次 SDK 返回 completed 仅代表该次会话调用结束。

## D1 在同一份回复上只改变一个处理步骤

各对照固定历史外显文本、题目和测试，切换锁定的 ACE / DSH 提取逻辑，或单独应用 ACE 的 `always_comb → always @*`。产出候选的路径统一在 Icarus 13.0、seed 20261122 下走 CVDP 原测试的本机 local_import。评分器逐字节核对受测文件。三条有历史受测候选的原路径均复现候选哈希和判定。

| 固定的历史回复 | 改变的步骤 | 对照结果 |
|---|---|---|
| 状态机，ACE＋GPT，重复 1，首轮 | 对已提取 RTL 替换一处 `always_comb` | 字节改变，两侧各通过 6 项原测试 |
| 状态机，DSH＋GPT，重复 1，首轮 | 对已提取 RTL 替换一处 `always_comb` | 字节改变，两侧都在 elaboration 失败，各有 8 条显式 cast 诊断 |
| Swizzler，ACE＋GPT，重复 1，首轮 | 切换提取器 | ACE 提取去掉模块前的 `timescale`，DSH 保留。两侧各通过 9 项原测试 |
| 通用计数器，DSH＋Flash，重复 1，第二轮 | 对同一份已完成的多代码块回复切换提取器 | DSH 未产出候选。ACE 提取出的 RTL 能编译并执行 8 项原测试，其中 Gray 码检查失败 |

**三个两侧均可评分的对照中，转换改变了受测字节，最终判定相同。** 计数器则出现了可归因于 Harness 提取规则的评分入口差异。V1 首轮功能失败、第二轮未交付的记录仍成立。替换第二轮提取器后，程序才进入仿真并暴露 Gray 码错误。

对所测状态机候选，ACE 无需转换也能通过，DSH 改用 `always @*` 后仍有相同的编译错误。现有证据无法进一步区分显式类型转换问题与编译器兼容性各自的影响。Swizzler 的同分只覆盖现有测试，不能据此推断删掉时间尺度声明在其他设计中等价。四份回复均用于病例诊断，不能估计整个矩阵出现这些现象的频率。

## 对训练任务与 Reward 的意义

计数器的同一条轨迹暴露了两种不同问题。提取失败能支持交付流程诊断。拿到可评分文件并重放后，才知道这份候选还存在 Gray 码行为错误。Gray 码错误目前由原测试支持，进入训练任务候选前仍需依据公开规格独立验证。

如果训练目标是 RTL 修复，任务应定义确定的交付格式，分别记录提交状态、实际受测 RTL 和功能判定。如果目标还包含遵守交付契约，可另设可检查的提交指标。环境采用兼容性后处理时，可用变换记录与前后字节区分环境处理的贡献和模型生成的代码。

## 复现

在持有 V1 私有运行目录与方法审计本地索引的工作副本中执行。D1 依赖项目已有的锁定 CVDP 源码、本机评分环境及 Icarus。两条命令各创建新的私有目录，并打印路径，无需模型凭据。

```bash
python3 scripts/audit_behavior.py
python3 scripts/replay_postprocess.py
```

D0 输出每个试次的 manifest.json、events.jsonl 和可公开的 summary.json。D1 保留私有候选与编译、仿真报告。公开的 public-summary.json 仅含判定、计数和哈希等可核对字段。公开 GitHub 读者可以核对摘要，逐请求复现需要原始私有记录。
